# 需求范围与追踪矩阵

产品 0.0.1 / 2026-09-16。读者：需求提出方、产品负责人、开发与测试负责人。以 22 项需求关联 66 个测试场景，明确实现依据和本轮待验收范围。

> 需求已纳入交付不代表验收通过。矩阵“当前依据”描述已有源码或历史验证；本轮接收方验收统一为未执行，待逐端执行并签收。范围和优先级由双方确认，本文不预填签字或承诺日期。

## 1. 范围与产品规则

信众、大师、寺院、商城与平台是业务角色，不等于五套独立工程。当前 H5 包含信众和大师入口；两套原生 iOS 分别构建；商城与平台在统一后台，寺院后台独立。产品功能、可用入口、数据归属和交付责任按角色核对。

统一账号形式为用户名 / 邮箱、密码、图片验证码。邮件用于注册、激活和找回。独立大师在大师端申请，寺院在寺院平台申请，纳管大师由寺院分配并在大师端激活。平台 admin 为内部账号，不开放公众自助注册。

预约主路径是待确认、待执行、执行中、待确认回执、信众确认完成。全院执行归寺院，不产生无大师私聊。心愿自愿，回执保留版本，历史无回执不补造。集中入口新增而原订单不移除。

支付、预约、制作加持、物流、退款、积分和成长值分别建模。确认接单不代表完成，取消不代表退款到账，消费积分不代表现金，模拟订单不代表真实营收。

## 2. 需求优先级与责任

产品负责人确认入口和体验；需求负责人确认业务规则及排除项；开发负责人确认版本和技术依赖；测试负责人组织执行和缺陷复验；实际业务方确认服务、商品和线下交付。一个人可承担多个职责，但签收时应逐项说明。

P0 用例覆盖核心闭环、身份隔离和账务状态一致性；P1 覆盖主要体验、运营及扩展依赖。需求矩阵按能力组织，执行时以用例优先级和实际放行范围为准；外部能力的依赖不能仅因优先级为 P1 被默认为可用。

## 6. 变更控制与追踪示例

新需求先填写用户问题、角色、入口、数据对象、正常路径、失败路径、权限与历史兼容，再明确是否改变金额、状态或其他端。产品和需求负责人确认验收条件后，由开发估算和安排，测试更新受影响用例。

例如“寺院全院预约也能私聊”是新沟通主体和权限模型，不是把被过滤会话重新展示。需先确定谁接收、人员交接、订单与会话绑定、未读口径、停用和隐私规则，再增加需求及用例。

例如“上链证明服务真实”涉及新的外部服务与证明边界。当前文件哈希不应改名冒充区块链；新增需求需定义记录对象、核验方式、成本、失败恢复和用户实际能得到的证明。

| 变更单字段 | 必须说明 |
| --- | --- |
| 变更 ID / 关联需求 | 原规则、提出原因与用户场景 |
| 范围 | 影响端、角色、接口、历史数据、外部依赖 |
| 验收 | 新用例及受影响回归、排除项 |
| 实施 | 负责人、估算、目标版本、迁移及回退 |
| 确认 | 需求批准人、产品确认、技术和测试意见 |
