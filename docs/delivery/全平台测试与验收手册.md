## 1. 先确定测试边界

接收文档后先由产品负责人、需求负责人、测试负责人确认本轮是“受控产品验收”还是“真实业务放行”。受控验收可以使用隔离数据与模拟渠道；真实业务放行必须补齐对应渠道、资金、交付和设备证据。测试许可范围、数据恢复方式、缺陷负责人需在开始前登记。

本套文档只交付方法、用例和已有证据摘要，本次没有新执行 66 个业务场景、创建生产订单或修改真实回执。原生最新本地补丁与线上 Web 版本不同，执行前必须固定各端版本。

用例优先级 P0 表示核心闭环、身份与对象授权、金额积分、状态与数据一致性；P1 表示主要体验、恢复和运营能力。优先级不是通过状态。

## 4. 推荐执行顺序

1. 准备阶段：核对四册与版本，建立账号和数据，确认媒体、邮箱和访问条件。条件缺失先登记阻塞。
2. 核心冒烟：T01、T06、T14、T16、T20、T23、T25、T39、T42、T45。覆盖能登录、能发现、能预约、能执行、能核对、能创作和能生成订单。
3. 业务验收：执行认证入驻、全院和大师两条履约、DIY、商城、积分、AI 与内容。不同主体不能只测其中一条。
4. 异常与隔离：执行越权、状态跳转、并发、重复提交、媒体非法、断网和账号切换；重点确认没有错误写入。
5. 跨端体验：将适用用例复制到 H5、信众原生、大师原生、两个后台的记录行，执行布局、主题、手势和恢复。
6. 放行复核：运行真实渠道、设备与恢复类用例所需条件；未具备就保留阻塞，不以演示通过替换。

建议先在隔离环境跑完整链路，再对批准的线上范围做必要验收。正式线上不得为了截图把真实订单推进到执行或完成，也不自动清空既有历史。

## 6. 如何记录结果与缺陷

执行记录的唯一键建议为“用例 ID + 端 + 环境 + 版本 + 执行轮次”。同一用例多端测试必须另起行，不把单端证据复用成全端结论。配套 CSV 已提供操作与预期，填入实际结果、结论、业务编号及证据位置。

结论只用“通过、失败、阻塞、未执行、不适用”。通过需每个断言均有实际结果；阻塞说明缺什么条件和负责人；不适用须由需求负责人确认理由。截图加 HTTP 200 不足以证明媒体可读、权限正确、支付到账或业务状态一致。

缺陷填写复现前提、输入、步骤、预期、实际和影响范围。S0 是数据泄露、越权写入或资金错误等阻断；S1 是核心链路不可完成或崩溃；S2 是有替代方式的主要功能问题；S3 是不阻断理解的视觉细节。严重度与 P0/P1 分开，修复后按原用例及受影响相邻流程复验。

例如 T16 若付款后出现空大师会话，登记私聊列表、原订单归属、进入错误、计数及版本；修复后同时复验列表、计数、深链失败页和正常大师会话。不能只隐藏一张卡就关闭相关问题。

## 9. 验收汇总和放行规则

建议受控验收的放行条件为：范围确认；全部纳入的 P0 在各适用端完成且通过；没有未关闭 S0/S1；P1 未完成项逐项说明影响、替代方式、责任人和复验日期。这是建议门槛，需接收双方确认后生效，不是已经获得的验收结论。

真实业务放行还需要选定场景的支付退款对账、真实物流或线下交付、用户支持责任，以及纳入范围的原生分发、APNs 或音视频验证。条件不足只可明确放行受控演示范围，不能附条件宣称整个平台正式商业化通过。

执行通过率 = 通过行数 / (通过行数 + 失败行数)。覆盖完成率 = 已执行行数 / 纳入范围行数，已执行仅包含通过和失败；阻塞、未执行计入纳入范围分母，不适用单列。分母为零显示“暂无结果”。同时列出 P0、各端和各模块结果，防止总体比例掩盖阻断问题。

| --- | --- |
