# 投资侧产品与验证说明

产品 0.0.1 / 信息截止 2026-09-16。读者：投资沟通参与者、合作决策人及产品负责人。

> 本册提供产品事实、经营假设和尽调材料清单。当前没有经核验的营收、真实支付转化、活跃用户、签约供给数量或估值数据；不以演示账号和模拟订单填补这些数据。本册不构成融资条款或经营业绩证明。

## 1. 一页产品摘要

问玄东方面向传统文化兴趣与服务需求，将 AI 参考、内容发现、寺院与大师供给、服务预约、过程回执和手串定制连接起来。产品侧重点从“能提交订单”延伸到“谁执行、进展如何、交付了什么、由谁确认”。

当前具备信众及大师 H5、两套原生 iOS 工程、统一运营管理台和独立寺院管理台。Web 已有部署和受控流程记录，信众 iOS 有签名安装和模拟器测试记录，完整原生业务验收仍待完成。普通支付渠道为模拟，真实商业闭环尚需验证。

| 决策问题 | 当前可回答 | 还不能回答 |
| --- | --- | --- |
| 产品是否只有静态原型 | 已有身份、订单、履约、媒体、跨角色操作和持久记录 | 不等于所有功能、环境均验收通过 |
| 是否形成真实供给网络 | 有寺院入驻、独立大师认证、寺院纳管流程 | 测试寺院和大师不代表签约合作伙伴 |
| 是否已跑通商业化 | 可验证定价展示、模拟下单与受控履约 | 真实收款、净收入、留存和复购尚无本册可用证据 |
| 是否具有可信交付 | 有阶段记录、版本、授权访问和用户确认 | 文件哈希不能证明线下事实，也不是区块链 |

## 2. 用户问题与产品假设

假设一：用户浏览内容后，需要明确的供给信息、服务说明、费用和可预约安排。产品用发现、筛选、详情和预约缩短信息寻找过程。要验证的不是页面点击是否多，而是用户能否独立找到并理解适合自己的服务。

假设二：远程服务只显示“确认”不足以形成交付理解。产品提供可选心愿、执行阶段、图文视频回执、补充要求和用户确认。要通过用户访谈和实际履约观察确认其是否减少疑问、返工或投诉；目前不宣称已提升信任率。

假设三：手串创作可成为文化兴趣与商品定制的入口。游客先编辑，账号承接保存和下单，后续以材料和订单快照交付。编辑活跃能否转化为真实购买仍待验证。

假设四：平台认证与寺院纳管两种供给模式可以共存。登录入口相同，认证来源、管理权和订单归属分离。是否提高供给效率应观察入驻耗时、审核返工、接单和交付指标。

## 3. 当前产品的差异化设计

| 设计选择 | 预期价值 | 验证方法 |
| --- | --- | --- |
| 跨角色执行闭环 | 信众知道服务如何推进，责任方可交接 | 观察从预约到回执确认的任务完成及问题原因 |
| 集中进度与原订单并存 | 无需反复寻找订单，历史仍可追溯 | 对比用户寻找进度任务耗时、成功率 |
| 双轨供给治理 | 寺院纳管与独立执业管理边界明确 | 跨寺院越权测试、入驻流程试点 |
| 游客 DIY 与真实 3D | 降低探索阻力、提高设计可理解性 | 测量创作保存、下单转化及设备性能 |
| 东方视觉与克制动效 | 让状态清晰且符合产品气质 | 用户可用性走查、减少动态效果测试 |

以上是产品取舍，不是已验证的竞争壁垒。竞争对手的公开观察日期、访问限制和推断位于配套《竞品研究与产品决策手册》；本册不增加未经重新研究的市场份额、行业规模或竞品营收数字。

## 5. 商业模式：待验证的选择

可讨论三类收入路径，但应按试点合同与实际能力选择，不能把所有路径同时视为已开通。第一类是商品及定制销售，第二类是约定的平台交易或服务收入，第三类是 AI 内容或权益服务。积分扣减本身不构成现金收入。

| 路径 | 可交付对象 | 需要验证的条件 |
| --- | --- | --- |
| 商品 / DIY | 商品或定制实物 | 供应成本、品质、工期、退换返工、真实收款与物流 |
| 预约平台服务 | 供给匹配、订单与履约协作 | 合作主体、责任、计费方式、回执与争议处理 |
| AI / 权益 | 参考内容及明确权益 | 用户价值、调用成本、内容质量、扣分与权益口径 |

定价、佣金、结算周期和收入确认需由项目的实际合同与财务口径确认。本册不设推荐费率、预测收入或投资回报，不将模拟订单金额视为市场需求证据。

单位经济性应按业务分别建立台账：约定净收入，扣除直接商品、制作、履约、渠道、模型调用和客服成本。退款已冲减收入时不要再次重复扣减。平台交易金额与平台收入应分别报表，消费积分、奖品预算与成长值分别记录。

## 6. 试点指标与数据要求

以下是建议采集口径，目标值由试点双方确认，当前不填虚构数值。每个指标必须附环境、周期、分母、去重方式和来源。

| 指标 | 建议计算口径 | 最小证据 |
| --- | --- | --- |
| 自助使用成功率 | 无协助完成目标任务人数 / 有效参与人数 | 任务脚本、完成结果、问题分类 |
| 预约交付率 | 到期应交付且已被确认完成的服务 / 到期应交付服务 | 排期、回执及用户确认；含逾期未完成项 |
| 回执补充率 | 至少申请过一次补充的预约 / 已收到最终回执预约 | 回执版本与补充原因 |
| DIY 保存率 | 成功保存账号设计的人数 / 进入编辑的人数 | 同一观察窗口，区分游客草稿和已保存 |
| 真实转化 | 发生可归因真实支付的人数 / 对应有效访问人数 | 真实交易渠道核对，排除内部及 mock |
| 留存与复购 | 同批用户在约定窗口回访 / 再次真实购买 | 成熟观察窗口，回访和复购分别统计 |
| 交付贡献 | 相应净收入减直接变动成本 | 财务、商品、履约和渠道记录 |

用户研究样本、任务数和发生环境必须如实披露。功能用例通过率不能替代产品满意度，满意度不能替代付费与留存。

## 7. 推进关卡与资源方向

第一关是受控验收：按测试手册验证身份隔离、主流程、失败恢复、媒体和账务语义，关闭阻断问题。交付物为用例记录、缺陷清单和确认范围。

第二关是真实业务准备：按选择的场景补齐真实支付和退款、对账、物流或服务交付、明确的售后责任；原生纳入试点时完成设备与分发验收。相关运营与专业审查由相应负责人给出结论，本册不作法律合规认证。

第三关是小范围真实试点：由真实且确认合作的供给方承接，保留真实交易、交付、成本和反馈证据；预先确定观察窗口与继续、缩小、暂停的判定条件。达到条件后再讨论扩大渠道和供给。

拟投入资源可按身份与履约质量、原生与外部能力验收、试点运营与客户支持、数据采集四类编制。人员、金额、周期和融资规模未确认，保持“待项目方确认”，不在本文推定团队规模或预算。
