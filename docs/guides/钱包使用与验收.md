# 钱包使用与验收

本期将已有支付、退款、收入与结算记录集中展示。钱包不是储值账户；不提供充值、转账、余额支付或真实提现。积分、优惠券和功德成长继续独立管理。

## 信众怎么用

在 H5 或原生 iOS 的“我的 → 我的钱包”进入。H5 地址为 `/c/wallet`。

- **渠道账单**展示支付记录中非 mock 的渠道记录，实际扣款和退款到账以支付渠道为准。
- **演示账单**展示 mock 支付与模拟退款，不能视为真实资金。
- 上方分别显示累计支付、已退款和退款处理中金额。累计支付是支付总额，未减去退款；待支付、失败和已关闭支付不计入累计支付。
- 在“全部账单 / 退款记录”切换。展开一笔账单，可见支付单号、订单编号、渠道、每笔退款的金额、原因、时间和状态。
- 预约账单直接回到关联预约；商城及 DIY 进入对应订单列表，根据展示的订单编号查找。原订单详情保持可用。
- 无记录时显示空态；读取失败显示错误与重试，金额显示“—”，不能当成零余额。

## 大师和寺院怎么用

大师 H5 及原生 iOS：“我的 → 我的钱包”，H5 地址 `/m/earnings`。寺院管理台：侧栏“寺院钱包”，地址 `/temple/wallet`。

钱包分为“待确认结算、已确认结算、账面已结算”。这些数字来自结算单，不是可提现现金，也不是银行回单。每笔结算展开后可核对本方分配金额、平台费用、应结金额和来源订单。

独立大师、寺院纳管大师都只查看分配给本人的份额；寺院管理员只查看本寺院份额。大师和寺院的钱包不会各自重复计入同一订单的全部金额。大师钱包保留“收入流水与趋势”，可查预约、咨询及加持等已记录收益，与结算单分别核对。

历史提现来自原有模拟流程。状态“模拟完成”不意味着银行打款；本期不提供新的提现操作，不收集银行卡。

## 接口与权限

| 接口 | 参数 | 归属 |
| --- | --- | --- |
| GET `/api/v1/payments/wallet` | `mode=channel/mock`、`filter=all/refunds`、`page` | JWT customer 的 userId |
| GET `/api/v1/finance/wallet/master` | `page` | JWT masterId 在服务端查出的业务编码 |
| GET `/api/v1/finance/wallet/temple` | `page` | JWT temple_admin 的 templeCode |

每页 20 条，按记录 ID 倒序；汇总不受当前分页影响。金额以整数分返回。服务方返回 `withdrawEnabled=false`、`recordMode=accounting_only`。不接受客户端的归属 ID，银行卡信息不会出现在响应中。读取错误不降级为成功的零值响应。

## 怎么测

1. 未登录直达钱包，应进入登录页，且不先发送钱包数据请求。
2. 客户 A 和 B 分别有订单，用 A 的令牌附带 B 的 `userId` 或 `X-User-Id`，只能看到 A 的数据。
3. 为同一支付单准备成功部分退款、处理中退款和失败退款。验证成功部分累计，处理中单列，失败不计入已退款；支付总额不因多笔退款而翻倍。
4. 分开准备 mock 和渠道记录，切换后汇总、列表同步变化。多页列表的总金额保持不变。
5. 同一预约划分大师和寺院份额，核对双方只能看自己的记录；寺院纳管大师不能访问寺院钱包接口。
6. 断开本机测试接口或返回 503，确认显示“—”与重试，恢复服务后重试成功。
7. 查看历史模拟提现，确认不会出现申请提现按钮或真实到账承诺。
8. 检查 320/390 像素 H5、管理台宽屏，切换筛选、展开明细、键盘焦点、浅深色主题；iOS 检查返回手势和原生导航。

自动化：后端 `wallet-mysql` CI 在独立 MySQL 测试支付汇总、部分退款、分页、跨账号和结算份额。H5 发布 CI 的钱包用例覆盖窄屏、明细、错误重试、访客保护与模拟提现提示。双 iOS 还需分别构建 workspace；不要直接构建未安装 Pods 的 xcodeproj。

部署前须由数据库管理员执行后端 `scripts/db/20260926_wallet_identity_permissions.sql`，仅授权财务账号读取大师表的 `id/code` 两列。自动二进制发布不会代为执行数据库授权。受限账号回归必须通过，不能只使用 root 测试代替生产权限验证。

2026-09-26 发布状态：信众钱包、寺院钱包已上线验证；大师钱包生产读取仍等待上述最小授权，暂不可视为已验收。双 iOS 源码已推送且无签名编译通过，未安装或发布 TestFlight。
