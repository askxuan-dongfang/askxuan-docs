## 1. 目标与范围

让管理人员从“今天要处理什么”进入工作，沿着机构/人员、实际服务、审核、订单与账务找到同一对象；基础标准有唯一维护入口，提供者资料能解释前台展示与筛选结果。

统一的是导航、对象关系、页面规范和追溯入口。寺院台继续独立，师傅端保持本人/纳管范围；服务预约、咨询、商城、DIY、积分订单保留各自数据和状态机，成长值、积分与现金分账。

2026-10-21 设计审查的历史现状以 frontend `ee7e48ee1f70b1d5b6adcb0c4147b5478b7793f2` 的[菜单](https://github.com/askxuan-dongfang/askxuan-frontend/blob/ee7e48ee1f70b1d5b6adcb0c4147b5478b7793f2/apps/web-platform-admin/src/layouts/DefaultLayout.vue)、[平台路由](https://github.com/askxuan-dongfang/askxuan-frontend/blob/ee7e48ee1f70b1d5b6adcb0c4147b5478b7793f2/apps/web-platform-admin/src/router/index.ts)、[商城路由](https://github.com/askxuan-dongfang/askxuan-frontend/blob/ee7e48ee1f70b1d5b6adcb0c4147b5478b7793f2/apps/web-platform-admin/src/commerce/routes.ts)为基线。下文“新增/建议”保留整体设计目标含义；历史 P0 以第 7 节及 P0 报告为准，2026-10-22 当前增量以第 8 节及本轮验收记录为准。超出两轮已测范围的目标仍是待办，现有地址可访问不等于完整业务已验收。

## 2. 职责与权限

以下保留 2026-10-21 P0 的内置身份与作用域基线；本轮自定义岗位只按第 8.3 节的明确可委派能力增补，不改变这些既有身份边界。

| 角色/载体 | 当前边界 | 新界面要求 |
| --- | --- | --- |
| `platform_super` | 可进入现有平台、商城及超级管理员专属路由；具体写入仍由后端核验 | 标准维护、认证入驻、AI 等专属功能不随菜单重组下放 |
| `platform_service` | 普通平台路由；不能据父级入口取得超级管理员或商城专属权限 | 仅呈现原有可访问对象与动作，不因“运营”命名扩权 |
| `shop_admin` | 显式授权的 `/commerce/*`，默认商城工作台；无普通平台权限 | 可处理获准的商品、材料、订单等；创作奖励、成长、AI 等不能默认开放 |
| 寺院台 | 独立 `/temple/`；本寺资料、服务、人员与履约；申请人受入驻路由限制 | 显示机构作用域，不让链接跳转绕过本寺限制 |
| 师傅 H5/原生 | 本人资料、服务和任务，受所属机构及业务规则约束 | 保留本人/纳管范围，不能直接编辑平台标准；身份、擅长是资料，不自动构成资质或服务能力 |

以上以[逐级路由授权](https://github.com/askxuan-dongfang/askxuan-frontend/blob/ee7e48ee1f70b1d5b6adcb0c4147b5478b7793f2/apps/web-platform-admin/src/router/access.ts)、[寺院端路由](https://github.com/askxuan-dongfang/askxuan-frontend/blob/ee7e48ee1f70b1d5b6adcb0c4147b5478b7793f2/apps/web-temple-admin/src/router/index.ts)及业务模型中的后端范围校验为准。导航隐藏不代替接口鉴权。

历史设计提出按“对象 × 查看/编辑/审核/结算/发布/导出 × 机构范围”细分职责，P0 当时不新增角色授权。本轮仅接通第 8.3 节明确可委派的岗位能力；其余完整能力矩阵仍待评审。原型的角色视角切换只展示差异，不修改账号或证明真实鉴权。

## 5. 关键流程

**初始归属在入驻 / 建档时建立。** 寺院由入驻经办人、独立师傅由本人在认证申请中选择五大类型及标准宗派 / 信俗；寺院纳管或平台代建师傅由有权管理方创建档案时选择，随后再分配 / 激活账号。单纯注册登录账号不等于审核通过或公开展示。选择现有标准项不授予申请人修改标准目录的权限。

设计审查时，这些入口已有主信仰和宗派字段，但入驻的宗派仍是 `sect` 文本、合同无标准多标签且仅四类，缺南传佛教；当时确认必须把“申请选择 → 审核有效版本 → 正式标准关联 → 目录筛选”接成同一条链，不能再由运营在不同页面独立补一份。纳管建档沿用现有审批边界，后续变更是否增加申请审核需另定，不能自动新增权限或审批环节。依据与验收见[业务模型](管理平台业务模型与迁移约定.md)。本原型尚未演练入驻表单和真实审核落库；四入口真实实现与验收属于第 7.1 节的 P0 历史基线及其报告，本轮新能力另见第 8 节与本轮验收记录。

**标准 → 提供者 → 前台。** 五类信仰、七码心愿和 S001—S013 服务保持既定范围，多信俗及历史 `sect/region` 不丢弃。先选标准归属，再配置实际服务与心愿例外；详情显示“资料文本”“筛选归属”“有效服务”三者差异，前台预览解释命中来源。修改前查看引用影响，分段保存并回读；统一原子保存、并发及重试协议仍待实施，不能把现有多请求写入说成事务。迁移细则和跨类历史关联待决项见[业务模型](管理平台业务模型与迁移约定.md)。

**审核待办 → 原队列处理。** 三种申请可汇入待办，但不是每个申请依次通过三个队列：认证入驻沿用 `draft/submitted/rejected/approved`；寺院沿用 `pending → first_pass → final_pass` 和驳回；师傅资质沿用 `pending/pass/rejected`。统一对象链接、证据浏览和操作历史，各自保留 API、修订/状态校验与副作用。依据：[认证入驻](https://github.com/askxuan-dongfang/askxuan-frontend/blob/ee7e48ee1f70b1d5b6adcb0c4147b5478b7793f2/apps/web-platform-admin/src/views/OnboardingReviewView.vue)、[寺院审核](https://github.com/askxuan-dongfang/askxuan-frontend/blob/ee7e48ee1f70b1d5b6adcb0c4147b5478b7793f2/apps/web-platform-admin/src/views/temple/TempleReviewView.vue)、[师傅资质](https://github.com/askxuan-dongfang/askxuan-frontend/blob/ee7e48ee1f70b1d5b6adcb0c4147b5478b7793f2/apps/web-platform-admin/src/views/master/MasterReviewView.vue)。

**订单 → 履约 → 售后/对账。** 聚合入口用“业务类型+原单号”定位。预约显示时段、执行方和回执；咨询显示会话与服务时长；商城显示商品、配送与退货；DIY 显示确认配方、制作和加持；积分订单显示积分消耗与兑换/领奖流程。仅提供跨页导航和关联追溯，各域决定能否取消、退款、发货、完成或评价，不改订单状态机。

**DIY 确认 → 不可变公开定稿。** 本人同款订单已真实付款且款式、用料、价格已确认后才允许发布；复制不继承发布资格。发布冻结配方、价格和来源版本，个人稿后续编辑不覆盖公开稿；退款、取消或下架按既有合同屏蔽新的公开使用/归因，保留历史订单与账务。管理界面展示不满足项，不新增人工绕过入口；完整合同见[定稿发布方案](DIY定稿发布与首页统一产品原型方案.md)。

**权益与 AI 分别生效。** 成长等级规则、积分活动和现金结算各保留规则版本及原单快照，不相互换算或合并余额。AI 沿用保存草稿、评测、固定版本、灰度、回滚流程；每个启用技能的正常用例需过现有门槛，自动断言通过还须检查回答质量。密钥不回显，留空保留现值，清除需明确操作。依据：[AI 发布与评测](https://github.com/askxuan-dongfang/askxuan-frontend/blob/ee7e48ee1f70b1d5b6adcb0c4147b5478b7793f2/apps/web-platform-admin/src/views/ai/AgentOperationsView.vue)、[连接配置](https://github.com/askxuan-dongfang/askxuan-frontend/blob/ee7e48ee1f70b1d5b6adcb0c4147b5478b7793f2/apps/web-platform-admin/src/views/settings/SettingsAiView.vue)。

### 8.3 渐进权限与真实审计

自定义平台岗位默认无权限，只能配置明确可委派的功能与操作。超级管理员、寺院、师傅、商城及申请人等既有身份和机构绑定边界不因菜单重组改变；AI 密钥、标准、备份、新服务聚合等尚未完成委派合同的模块继续限超级管理员，不用自定义角色伪装该身份。

角色授权、账号角色 / 绑定 / 启停采用数据库版本；授权或绑定更新与版本递增同事务提交。access 和 refresh 均携带签名的角色 ID、账号版本、角色版本与授权 scope；只有 access 包含 `permissions` 权限快照。refresh 不增加角色列表、客户端字段或权限列表，续期重新读取有效身份和授权并核对版本。网关对管理访问实时核对认证服务的有效状态和版本，过期授权必须拒绝。原 SID、密码修改和登出 epoch 机制保留，旧内置会话的零版本兼容不得成为授权更新后的绕过入口。具体可委派目录及迁移清单随实现逐项验收，不仅验证菜单隐藏。

操作日志使用独立管理写操作记录，不再把审核队列冒充全平台操作审计。网关对已验证的管理写请求记录操作人 ID、安全资源标识、方法、结果和关联编号；不保存请求 / 响应正文、query、密码、邮箱、密钥或令牌。审计写入仅经网关到审核服务的内网认证接口，不能通过公网网关路由提交伪造日志。

写操作开始前，审计起始记录持久化失败须阻止业务动作。业务已成功但审计终态补写失败时，保留真实业务响应并显式标记审计待核对，不伪报业务失败或自动重试资金操作。拒绝、业务错误、HTTP 错误和结果未知分别记录；日志接口不替代原审核历史。

### 8.4 独立模拟打款测试

用户确认使用 ECS 独立测试入口 `/admin/finance/payout-sandbox`，只允许超级管理员操作。页面、虚拟收款对象、状态和结果全程明确显示“模拟”，禁止填写真实银行卡、收款账号、收款人或自由备注。页面以元输入，范围 0.01–10000.00 元、最多两位小数，接口与数据库使用整数分。

模拟实例与事件分别保存在 `payout_sandbox` 和 `payout_sandbox_event`，编号以 `sandbox_` 开始。该链路不读取或改写正式提现、结算、交易与余额账本，不发送银行请求或业务 MQ。正式提现接口继续明确返回通道未接入，不能借模拟按钮把正式提现改为成功。

演练流程为待审核 → 审核通过 / 拒绝 → 提交模拟。提交后依次记录模拟处理中和模拟回执，结果可选成功、失败、超时未知。只有明确失败才能重试；超时未知必须先通过“模拟查单”确认为成功或失败，不能直接重复支付。创建和动作均有请求幂等号、数据库版本与事务事件，重复请求不能生成第二次处理，旧版本或内容冲突须拒绝并回读。

接口精确限制为 `GET/POST /api/v1/admin/finance/payout-sandbox`、`GET /:id`、`POST /:id/actions`。它是测试能力，不能用该测试结果证明真实银行打款或渠道对账通过。
