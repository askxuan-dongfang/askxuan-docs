## 1. 目标与范围

让管理人员从“今天要处理什么”进入工作，沿着机构/人员、实际服务、审核、订单与账务找到同一对象；基础标准有唯一维护入口，提供者资料能解释前台展示与筛选结果。

统一的是导航、对象关系、页面规范和追溯入口。寺院台继续独立，师傅端保持本人/纳管范围；服务预约、咨询、商城、DIY、积分订单保留各自数据和状态机，成长值、积分与现金分账。

设计审查现状以 frontend `ee7e48ee1f70b1d5b6adcb0c4147b5478b7793f2` 的[菜单](https://github.com/askxuan-dongfang/askxuan-frontend/blob/ee7e48ee1f70b1d5b6adcb0c4147b5478b7793f2/apps/web-platform-admin/src/layouts/DefaultLayout.vue)、[平台路由](https://github.com/askxuan-dongfang/askxuan-frontend/blob/ee7e48ee1f70b1d5b6adcb0c4147b5478b7793f2/apps/web-platform-admin/src/router/index.ts)、[商城路由](https://github.com/askxuan-dongfang/askxuan-frontend/blob/ee7e48ee1f70b1d5b6adcb0c4147b5478b7793f2/apps/web-platform-admin/src/commerce/routes.ts)为基线。下文“新增/建议”保留整体设计目标含义；本轮 P0 实现和部署以第 7 节与本轮报告为准，超出 P0 的页面能力仍待实施。现有地址可访问不等于完整业务已验收。

## 2. 职责与权限

| 角色/载体 | 当前边界 | 新界面要求 |
| --- | --- | --- |
| `platform_super` | 可进入现有平台、商城及超级管理员专属路由；具体写入仍由后端核验 | 标准维护、认证入驻、AI 等专属功能不随菜单重组下放 |
| `platform_service` | 普通平台路由；不能据父级入口取得超级管理员或商城专属权限 | 仅呈现原有可访问对象与动作，不因“运营”命名扩权 |
| `shop_admin` | 显式授权的 `/commerce/*`，默认商城工作台；无普通平台权限 | 可处理获准的商品、材料、订单等；创作奖励、成长、AI 等不能默认开放 |
| 寺院台 | 独立 `/temple/`；本寺资料、服务、人员与履约；申请人受入驻路由限制 | 显示机构作用域，不让链接跳转绕过本寺限制 |
| 师傅 H5/原生 | 本人资料、服务和任务，受所属机构及业务规则约束 | 保留本人/纳管范围，不能直接编辑平台标准；身份、擅长是资料，不自动构成资质或服务能力 |

以上以[逐级路由授权](https://github.com/askxuan-dongfang/askxuan-frontend/blob/ee7e48ee1f70b1d5b6adcb0c4147b5478b7793f2/apps/web-platform-admin/src/router/access.ts)、[寺院端路由](https://github.com/askxuan-dongfang/askxuan-frontend/blob/ee7e48ee1f70b1d5b6adcb0c4147b5478b7793f2/apps/web-temple-admin/src/router/index.ts)及业务模型中的后端范围校验为准。导航隐藏不代替接口鉴权。

未来可按“对象 × 查看/编辑/审核/结算/发布/导出 × 机构范围”细分运营、审核、财务、内容与系统职责；这是待评审的能力矩阵，不新增角色授权。原型的角色视角切换只展示差异，不修改账号。

下表定义目标页面，超出既有功能的部分均需后续开发。角色简称：超管 S、现有平台岗位 P、商城 M、寺院 T、师傅 R；表示工作归属，不是新增接口权限。

| 页面/面板 | 必要字段与操作 | 页面特有反馈 | 角色 |
| --- | --- | --- | --- |
| 工作台 | 业务类型、对象、待办原因、发生时间、负责人、最新同步时间；进入原业务 | 分区加载，某域失败不把总数写成 0；无待办与无权限分开 | S/P/M，各自范围 |
| 提供者列表 | 编码、名称、管理方、信仰/多信俗、标准地区、认证/经营/封禁状态、已启用服务；搜索、固定标准筛选、分页 | 零结果保留筛选和完整选项，清除单项不清空其他条件 | S/P；T 为本寺 |
| 提供者详情 | 基础资料、标准归属、服务、材料、操作历史；显示历史 `sect/region` 原文与地区继承来源 | 各段独立保存；部分成功明确指出，失败草稿保留；版本冲突先刷新比较 | 按既有字段权限 |
| 提供者服务 | 标准编码、名称、提供者、价格、启停、时段/容量、资格及心愿来源；查看有效配置 | 标准服务、实际服务和咨询区分；停用后保留历史订单 | S/P 依现权；T/R 依原端 |
| 认证与入驻 | 申请类型、经办人/本人、授权材料、修订号、审核意见与历史 | 退回必须给原因；材料不可读时提示失败，重复提交或过期版本不伪成功 | S |
| 寺院双阶段审核 | 申请编号、寺院、材料、初审/终审记录 | 初审通过只进终审；已处理隐藏无效动作 | 原审核角色 |
| 师傅资质审核 | 师傅/所属寺院、资质材料、审核结果 | 与认证、上架、平台封禁分别展示，不能一键互相替代 | 原审核角色 |
| 分类订单入口与详情 | 业务类型+原单号、用户、提供者、业务/支付/售后状态、各自金额单位、时间线、原单链接 | 独立查询失败单独重试；动作回原域，跨域无统一“完成/退款”按钮 | 各域原有角色 |
| 商品/材料/DIY | 商品分类、规格、库存、素材、售价；DIY 配方、用料、确认价、制作/加持/物流与定稿来源 | 缺料/价格变化明确阻止确认；草稿、订单、公开定稿不互相覆盖 | S/M |
| 财务与权益 | 业务来源、账本类型、币种/单位、实付/退款、观察期、对账差异、规则版本 | 成长值/积分/现金分别展示；只在各域允许时调整，不把预估当可提现 | S/P/M 按原授权 |
| 首页/内容 | 内容对象、落地目标、展示次序、启停、预览；分类引用标准编码 | 草稿与当前展示分开；无内容不填造默认业务数据，失败保留编辑 | 原内容角色 |
| AI 工作区 | 配置 revision、模型连接、知识范围、工具、评测、版本/灰度与运行记录 | 密钥只显示是否配置；未保存/评测未过不可发布，冲突保留草稿 | S |
| 基础标准 | 编码、名称、所属类型、启停、排序、引用对象及影响；心愿继承/自定义 | 编辑不改编码；停用不删关联；自定义空选不等于继承；编码从完整目录读取 | S 的既有标准权限 |
| 系统/审计 | 账号状态、角色/范围、操作人、对象、动作、前后值摘要、时间、结果 | 越权拒绝；日志不含密钥/私密材料；备份状态不等于恢复演练成功 | 原系统角色 |

**共用状态**：首次载入显示骨架/进度；空数据提供适当下一步，无搜索结果提供清除条件；失败说明受影响范围并重试；保存中冻结该动作、防重复，成功后回读有效值；无权限保留可理解的访问结果；对象删除/下架显示原因并可返回列表。表单离开提示未保存段，取消不提交。页面返回恢复筛选、页码与滚动位置。

桌面用稳定侧栏、内容区和按需详情抽屉；窄屏改导航抽屉和任务卡片，不把桌面表格整体缩小。浅深主题和简繁/跟随系统沿用全平台设置；文本、金额和状态可换行，焦点可见，控件可键盘操作。普通筛选和取消采用轻量样式，提交结果用文字/状态共同表达。

## 5. 关键流程

**初始归属在入驻 / 建档时建立。** 寺院由入驻经办人、独立师傅由本人在认证申请中选择五大类型及标准宗派 / 信俗；寺院纳管或平台代建师傅由有权管理方创建档案时选择，随后再分配 / 激活账号。单纯注册登录账号不等于审核通过或公开展示。选择现有标准项不授予申请人修改标准目录的权限。

设计审查时，这些入口已有主信仰和宗派字段，但入驻的宗派仍是 `sect` 文本、合同无标准多标签且仅四类，缺南传佛教；当时确认必须把“申请选择 → 审核有效版本 → 正式标准关联 → 目录筛选”接成同一条链，不能再由运营在不同页面独立补一份。纳管建档沿用现有审批边界，后续变更是否增加申请审核需另定，不能自动新增权限或审批环节。依据与验收见[业务模型](管理平台业务模型与迁移约定.md)。本原型尚未演练入驻表单和真实审核落库；本轮真实实现与验收见第 7.1 节及本轮报告。

**标准 → 提供者 → 前台。** 五类信仰、七码心愿和 S001—S013 服务保持既定范围，多信俗及历史 `sect/region` 不丢弃。先选标准归属，再配置实际服务与心愿例外；详情显示“资料文本”“筛选归属”“有效服务”三者差异，前台预览解释命中来源。修改前查看引用影响，分段保存并回读；统一原子保存、并发及重试协议仍待实施，不能把现有多请求写入说成事务。迁移细则和跨类历史关联待决项见[业务模型](管理平台业务模型与迁移约定.md)。

**审核待办 → 原队列处理。** 三种申请可汇入待办，但不是每个申请依次通过三个队列：认证入驻沿用 `draft/submitted/rejected/approved`；寺院沿用 `pending → first_pass → final_pass` 和驳回；师傅资质沿用 `pending/pass/rejected`。统一对象链接、证据浏览和操作历史，各自保留 API、修订/状态校验与副作用。依据：[认证入驻](https://github.com/askxuan-dongfang/askxuan-frontend/blob/ee7e48ee1f70b1d5b6adcb0c4147b5478b7793f2/apps/web-platform-admin/src/views/OnboardingReviewView.vue)、[寺院审核](https://github.com/askxuan-dongfang/askxuan-frontend/blob/ee7e48ee1f70b1d5b6adcb0c4147b5478b7793f2/apps/web-platform-admin/src/views/temple/TempleReviewView.vue)、[师傅资质](https://github.com/askxuan-dongfang/askxuan-frontend/blob/ee7e48ee1f70b1d5b6adcb0c4147b5478b7793f2/apps/web-platform-admin/src/views/master/MasterReviewView.vue)。

**订单 → 履约 → 售后/对账。** 聚合入口用“业务类型+原单号”定位。预约显示时段、执行方和回执；咨询显示会话与服务时长；商城显示商品、配送与退货；DIY 显示确认配方、制作和加持；积分订单显示积分消耗与兑换/领奖流程。仅提供跨页导航和关联追溯，各域决定能否取消、退款、发货、完成或评价，不改订单状态机。

**DIY 确认 → 不可变公开定稿。** 本人同款订单已真实付款且款式、用料、价格已确认后才允许发布；复制不继承发布资格。发布冻结配方、价格和来源版本，个人稿后续编辑不覆盖公开稿；退款、取消或下架按既有合同屏蔽新的公开使用/归因，保留历史订单与账务。管理界面展示不满足项，不新增人工绕过入口；完整合同见[定稿发布方案](DIY定稿发布与首页统一产品原型方案.md)。

**权益与 AI 分别生效。** 成长等级规则、积分活动和现金结算各保留规则版本及原单快照，不相互换算或合并余额。AI 沿用保存草稿、评测、固定版本、灰度、回滚流程；每个启用技能的正常用例需过现有门槛，自动断言通过还须检查回答质量。密钥不回显，留空保留现值，清除需明确操作。依据：[AI 发布与评测](https://github.com/askxuan-dongfang/askxuan-frontend/blob/ee7e48ee1f70b1d5b6adcb0c4147b5478b7793f2/apps/web-platform-admin/src/views/ai/AgentOperationsView.vue)、[连接配置](https://github.com/askxuan-dongfang/askxuan-frontend/blob/ee7e48ee1f70b1d5b6adcb0c4147b5478b7793f2/apps/web-platform-admin/src/views/settings/SettingsAiView.vue)。

评审按“找待办 → 定位提供者 → 理解标准/资料区别 → 修改单段并处理失败 → 回看前台效果 → 进入对应审核/订单”走查。重点确认九区归属、岗位职责、保留字段名称、历史冲突处理和保存策略。原型用例与后续真实验收分别记录，不以示例角色切换证明鉴权。

原型用“资料与允许修改的标准归属”“服务”两段演练成功与失败。生产若仍分别调用资料、标准关联和地区接口，应进一步拆成有独立反馈的保存段；只有明确的一致性命令才能合并反馈，不能照搬内存操作而宣称多个现有接口具有原子性。

### 7.1 本轮 P0 的确定合同

- 初始归属覆盖寺院入驻审批、独立大师认证审批、寺院新建大师、平台新建大师。沿用五类信仰及当前 24 项宗派 / 信俗标准目录；新建、提交和批准时选择 1—12 项同父且 `enabled` 的 `tradition`，草稿可空。`taoism` 接收后归一为 `daoism`；`sect` 展示为“宗派补充说明”，不从其内容推断或回填关联。
- `WorkProfile` 增量增加 `traditionCodes[]`。旧 `submitted` 申请缺失编码时批准明确失败，状态仍为 `submitted`；审核人员通过现有退回流程让申请人补填，不自动生成关联或绕过审核。审核与新建的资料、关联及既有数据库副作用在同一事务中提交。
- 更新省略或传 `null` 的关系字段保留原关联。普通文字编辑保留历史停用、未知或跨父关系；主信仰改动若与保留关系冲突则拒绝，界面不自动清空。已有关系修改仍只允许 `platform_super`；本轮不新增提供者归属变更申请。
- 公开 `GET /api/v1/beliefs/directory-tags` 返回 `data.list`，每项为 `code/group/beliefCode/name/value/sort/status`，只含启用项；管理端全量目录继续用于维护和历史解释。24 项是当前标准基线，公开响应数量随启停变化。平台寺院和大师列表的 `traditionCode` 在 SQL 过滤后计数及分页，不对一页结果再做客户端筛选。
- 管理端接入九工作区导航、资料及标准来源说明、敏感词字典解释、真实审核类型标签和固定筛选。师傅详情资料、标准关联和服务维持各自写入边界；资料和服务独立显示结果与失败草稿，只重试失败段，不承诺多个接口原子提交。后续统一保存及版本冲突协议属于 P1。
- 寺院共享入驻表单、H5 大师认证及实际 iOS 大师端 `MasterOnboardingView` 使用标准多选；原生构建、模型测试和实际 UI 操作分别验收，不以原型或源码检查替代。
- 数据库仅增补五条最小授权：既有 `auth_user`、`master_user` 的四条表级权限，以及 `temple_user` 对 `askxuan_master.master.belief_code` 的列级读取（原已可读 `code`）。目录与跨服务核验用共享锁，不授予额外目录写权；无目录重建、关系回填或历史清理。部署须先保存实际 `SHOW GRANTS`，核对账号及 host 后应用并回读。资金、订单及原有机构 / 本人作用域保持既定合同。
