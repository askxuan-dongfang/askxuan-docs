# 问玄东方全端一致性审计报告

> 审计日期：2026-09-04
> 范围：需求 PDF、产品原型、五个正式客户端、H5、备用客户端、20 个后端服务、321 个运行时 HTTP 契约、数据库/迁移、中间件脚本与 43 份 Markdown
> 当前结论：本地核心业务可继续联调，但不能声明“所有功能和生产能力全部对齐”

## 1. 总体判断

《需求文档-App改进》的六项改进都已具备原型落点、正式客户端入口、后端接口和数据库结构。预约计价、结构化时段、容量占位、gRPC 校验和本地模拟支付也已形成主闭环。

本次全面审查同时发现并修复了会造成错误结论的问题：网关管理角色越权、DIY 运行时样例数据回退、DIY 加持服务管理与计价数据分叉、制作完成与加持任务非事务、法师服务自动完成加持并生成假凭证、DIY 假微信/支付宝入口、预约完成后 C 端无评价入口、macOS 下 OpenIM 启动进程不能稳定脱离终端，以及多份文档仍称业务数据在内存中。

当前仍有生产阻断项和次要页面缺口，因此本报告不恢复“代码、原型和文档全部一致且可保证所有模块正常”的结论。

### 3.1 寺院服务标准目录

可提供的寺院服务类型固定为 `S001-S013` 共 13 项。寺院管理台以标签矩阵选择开通，不提供自定义编码或名称输入；可维护价格、结构化时段容量、诉求标签和上下架状态。后端通过代码白名单及 `service_type` 字典双重校验，C 端寺院列表按 `serviceCode` 精确筛选，寺院详情仅显示该寺院已开通且上架的服务。

### 3.2 寺院详情与管理账号

C 端寺院详情、平台寺院详情和寺院管理台读取同一 `askxuan_temple` 主数据。公开详情返回寺院、图册和上架服务聚合对象；初始化与幂等迁移为 10 座演示寺院补齐封面图记录。每座寺院均有独立寺院管理员账号及 `temple_admin` 绑定；T005 仍在待审核状态，因此账号预建但停用且 C 端不可见。平台账号管理页负责创建、改绑和启停，写入关系使用事务避免账号表与寺院关系表分叉。

10 座寺院/宫观使用真实名称、地址、简介与具备来源许可记录的实景照片；10 位大师均为明确标注的虚构演示人物。每位大师预置一个唯一 Master App 账号，平台管理台负责审核和账号分发，寺院管理台负责本寺院大师资料建档；账号启用与登录实时复核大师和所属寺院状态。平台大师列表使用独立全量接口，不再误用 C 端公开可见列表。

### 3.3 H5 与 iOS 体验对齐口径（2026-09-03）

- 对齐标准是相同业务入口、权威数据源、计价、支付、状态机、权限、空态、失败提示和重试行为，不要求像素级或系统手势实现相同。
- C 端已对齐收藏/私聊/大师广场三入口、直播观看、商城订单详情、资料与地址编辑、评价入口；法师端已对齐内容上传、草稿/审核/下架和直播能力检测/开始/结束。
- 法师日历在 iOS/H5 均可读取并写回同一排班接口；“设置休息日”以清空当日可约时段实现，H5 已删除仅在本地显示成功的请假表单。
- iOS 二级页隐藏底部导航并使用原生侧滑返回，H5 使用浏览器历史返回；iOS 使用 PhotosPicker，H5 使用 file input。这些是等价的平台原生交互，不是功能缺口。
- 共享后端尚未具备的生产能力不会在任一客户端伪造：真实支付、生产直播、账户资产/安全等仍按本报告风险项处理。

## 4. 预约与加持专项

预约创建以 JWT 用户为准，booking-service 通过 `temple.rpc:9083`、`master.rpc:9084` 和 `payment.rpc:9090` 获取权威服务/法师/支付信息。服务费与功德金由服务端形成价格快照；日期时段使用条件更新占位，取消和支付超时释放一次；本地 `mock` 支付成功后进入寺院待确认。

支付成功先由 finance-service 将全额记入平台总账和客户资金托管科目，不直接增加大师收入。预约履约并由用户评价结案后，平台读取可运营配置的预约抽成比例：服务费净额进入大师应付，功德金净额进入寺院应付，平台抽成与两方净额严格对平付款总额。实测 ¥201 在 12% 配置下分为平台 ¥24.12、大师应付 ¥176.00、寺院应付 ¥0.88；端到端验收为 21/21。

即时咨询不依赖预约：平台为每位法师维护开关、单次价格、有效小时和响应分钟；booking-service 保存不可变报价快照并通过 payment gRPC 以 `consultation:<orderNo>` 幂等模拟支付。全额先进入平台总账，默认咨询抽成 20%，剩余进入法师应付及收益明细。咨询在有效期内可发送，到期后只读历史；预约服务仍按服务、日期、时段独立下单。

DIY 制作完成时使用下单保存的设计快照判断是否加持。服务上架校验、订单状态和 `blessing_task` 创建在同一事务提交；法师必须在工作台执行“接受、开始、上传真实凭证并完成”，MQ 消费不再自动完成任务。

DIY 编辑器以 `designData.version=2` 保存腕围、余量、线材和有序 `beads[]`，并保留聚合 `items[]` 兼容设计广场下单。客户端价格只作即时预估；下单仍由 diy-service 按材料/SKU、上下架和库存重新计价。商城管理台是材料名称、材质、珠型、尺寸、颜色、纹理、工艺、通透度、图片、价格、库存和上下架状态的权威维护入口，H5 与 iOS 均从接口动态渲染；当前初始化目录含 45 项水晶、玉石、木质、菩提籽、陶瓷、金属、琉璃、织物与绳线等东方材料。

预约评价的权威写入口是 `/api/v1/bookings/:id/review`，校验 JWT 所有权和 completed 状态。booking-service 持久化后写入稳定事件键的 outbox，relay 失败重试，补偿扫描会从 `booking_status_log + booking_review` 重建缺失事件；review-service 通用评价自身的 MQ 生产仍属下一批 outbox 迁移范围。

## 6. 数据与逻辑质量

- 预约、DIY、商城、支付、评价、审核、财务和营销主实体使用 MySQL，不再以内存 Map 作为事实源。
- DIY 材料和加持服务管理与计价读取同一业务库；C 端接口失败时不再展示样例订单或地址。
- 网关对 `platform_super`、`shop_admin`、`temple_admin`、`master` 做路径级角色校验，平台超管保留全局覆盖。
- 前向迁移在增加唯一键前先处理存量重复数据；`blessing_task.diy_order_no` 新增唯一约束防重复任务。
- 支付金额仍由订单域校验，客户端金额和用户 ID 不作为权威依据。
- 寺院报表以 booking 已支付事实为源，商城报表以 order/item/return 为源，财务报表以平台总账收退款、结算净额和已成功提现为源；统计结束日按自然日包含。
- MQ 监控和 RabbitMQ 中断演练入口见 [MQ 可靠投递、监控与故障演练](../guides/MQ可靠投递监控与故障演练.md)。
