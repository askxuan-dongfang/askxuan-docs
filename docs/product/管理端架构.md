## 1. 产品全景

问玄东方是一个多端协同的佛道教文化服务生态平台，由以下5个产品组成，共同覆盖用户、寺院、法师、商城运营和平台管理五大角色的完整业务闭环。

### 1.2.1 五端协作关系矩阵

5 个产品端本质是 **5 种角色** 的协作关系，核心是"平台→服务提供方→消费者"的三层架构。

**层级关系**：

```
┌─────────────────────────────────────────┐
│  ⑤ 平台管理台（platform-admin）          │  超级管理者，监管一切
│  角色：平台运营 / platform_super          │
└──────────┬──────────────────┬───────────┘
           │ 审核/结算         │ 审核
           ▼                  ▼
┌──────────────────┐  ┌──────────────────┐
│ ② 寺院管理台      │  │ ④ 商城管理台      │  服务提供方
│ (temple-admin)   │  │ (shop-admin)     │
│ 角色：寺院管理员   │  │ 角色：商城运营     │
└────────┬─────────┘  └────────┬─────────┘
         │ 派单/管理            │ 派发加持任务
         ▼                     │
┌──────────────────┐           │
│ ③ 法师工作台      │◄──────────┘  执行方
│ (ios-master)     │
│ 角色：法师/道长    │
└────────┬─────────┘
         │ 提供服务
         ▼
┌──────────────────┐
│ ① C端用户App      │  消费者
│ (ios-customer /  │
│  mobile-customer)│
│ 角色：信众用户     │
└──────────────────┘
```

**协作关系矩阵**：

| 发起方 → 接收方 | 关系性质 | 触发场景 |
|---|---|---|
| ① C端用户 → ② 寺院端 | 消费→接单 | 用户预约法事服务，寺院管理台接单 |
| ① C端用户 → ④ 商城端 | 消费→制作 | 用户下 DIY 订单，商城运营制作手串 |
| ② 寺院端 → ③ 法师端 | 派单→执行 | 寺院把预约/加持任务分配给法师 |
| ④ 商城端 → ② 寺院端 | 委托→执行 | DIY 手串需开光，商城向寺院发加持任务 |
| ④ 商城端 → ③ 法师端 | 委托→执行 | 加持任务具体指派法师执行 |
| ②③④ → ⑤ 平台端 | 申请→审核 | 寺院入驻、法师认证、内容发布均需平台审核 |
| ②③④ → ⑤ 平台端 | 业务→结算 | 平台统一财务结算（5 端分账） |
| ⑤ 平台端 → ②③④ | 监管→下架 | 平台可强制下架违规寺院/法师/商品 |

> 三条核心业务线的端协作流（预约祈福流 / DIY 手串流 / 入驻审核流）详见第 4 章「数据流转关系」。

### 1.2.2 数据所有权边界

| 数据域 | 主 owner | 其他端的访问权限 |
|---|---|---|
| 用户资料/地址 | ① C端 | ⑤ 平台端只读 |
| 寺院信息/服务/排期 | ② 寺院端 | ① C端浏览、⑤ 平台审核 |
| 法师资料/排期/收益 | ③ 法师端 | ② 寺院端管理、⑤ 平台审核 |
| 商品/DIY 材料/订单 | ④ 商城端 | ① C端浏览、⑤ 平台只读 |
| 加持任务 | ④ 商城端创建 → ② 寺院端接 → ③ 法师端执行 | 三方协同，状态机驱动 |
| 财务结算/提现 | ⑤ 平台端 | ②③④ 申请提现，⑤ 审核发放 |
| 站内消息/公告 | ⑤ 平台端发布 | ①②③④ 消费 |

**技术层面的耦合关系**：

| 维度 | 实现 |
|---|---|
| 通信方式 | 5 端均通过 gateway (8080) HTTP REST + JWT，无直接端到端通信 |
| 身份隔离 | JWT Claims 携带 `UserType`（user/master/admin）+ `Roles` + `ClientID` + `TempleID`/`MasterID` |
| 事件驱动 | 9 个 RabbitMQ exchange fanout 广播，端间通过 MQ 事件解耦（如 booking.events 同时通知 message/finance） |
| 数据库隔离 | 每服务独立库（askxuan_xxx），跨库通过 MQ 事件同步，无直接跨库查询 |

> **核心要点**：5 端从未直接通信，所有协作通过 **gateway 同步调用 + RabbitMQ 异步事件** 完成。平台端是监管中枢，寺院端和商城端是服务提供方，法师端是执行方，C 端是消费方。

### 2.3 权限设计原则

1. **数据隔离**: 寺院管理员仅可操作本寺院数据，法师仅可操作本人数据
2. **最小权限**: 商城运营仅管理电商相关模块，不涉及寺院和法师业务
3. **审核分离**: 平台超管负责审核决策，客服负责前端问题处理
4. **财务分级**: 各角色可查看自身收入，但仅超管可操作结算和抽成配置
5. **操作审计**: 所有敏感操作（封禁、结算、权限变更）需记录审计日志

| 字典管理 | 维护教派、职位、宗派、地区等运营字典；服务类型仅查看固定 13 项标准目录 |
| 参数配置 | 平台级参数配置（抽成比例、结算周期、预约超时时间等） |
| 操作日志 | 全平台操作审计日志，支持按角色/操作类型/时间查询 |
| 数据字典 | API接口文档、数据结构说明 |
| 系统监控 | 服务健康状态、接口响应时间、错误率 |

账号管理以“一主体一独立账号”为演示基线：每座寺院至少有一个绑定 `temple_id` 的寺院管理员账号，也允许后续按岗位增加多个账号。平台负责创建、改绑和启停；寺院管理员只能管理 JWT 所绑定的本寺院。待审核或封禁寺院账号必须停用，终审通过后方可由平台启用。

### 5.2 统一API网关

| 方面 | 建议 | 说明 |
| ---- | ---- | ---- |
| 网关选型 | go-zero gateway | 与 go-zero 生态无缝集成；路由与中间件由 goctl 生成 |
| 版本管理 | URL路径版本号（`/api/v1/`） | 兼容多版本并行 |
| 限流策略 | 按端/按用户/按接口分级限流 | 保护后端服务稳定性 |
| 鉴权方式 | JWT Token + OAuth 2.0 | 统一认证，Token自动续期 |

| 接口分组 | 按业务域分组（`/temple/`、`/master/`、`/order/`、`/shop/`） | 清晰的接口边界 |

### 5.3 统一用户体系（SSO）

| 设计要点 | 说明 |
| -------- | ---- |
| 统一用户中心 | 所有端共用同一套用户体系，通过手机号唯一标识 |
| 登录方式 | 手机号+验证码 / 微信授权 / Apple ID（iOS端） |
| Token机制 | JWT Access Token（2小时）+ Refresh Token（7天） |
| 角色切换 | 同一账号可绑定多个角色（如既是法师又是商城运营） |
| 端标识 | 每个端分配独立的client_id，网关按端校验权限 |
| 登出机制 | 统一登出接口，清除所有端Token |

**角色绑定关系**:

```
用户账号 (手机号)
├── 角色: C端用户 ──── P01 问玄东方App
├── 角色: 寺院管理员 ── P02 寺院管理台 (需绑定寺院ID)
```

### 5.4 数据库设计要点

**当前方案**: 按业务域独立数据库 + 服务接口隔离

| 方案 | 优点 | 缺点 | 适用场景 |
| ---- | ---- | ---- | -------- |
| 共享库 + 租户ID隔离 | 统一管理、运维简单 | 跨域联表扩大权限和故障范围 | 仅保留兼容初始化数据 |
| **独立数据库** | 领域边界清晰、最小权限、可独立演进 | 需维护服务契约和最终一致性 | 当前：21 个业务库 |
| 分库分表 | 水平扩展能力强 | 开发复杂度高 | 数据量极大时 |

**核心数据表设计**:

| 数据域 | 核心表 | 说明 |
| ------ | ------ | ---- |
| 用户域 | `user` / `user_profile` / `user_auth` | 用户基本信息、认证信息 |
| 寺院域 | `temple` / `temple_image` / `temple_admin` | 寺院信息、图片、管理员绑定 |
| 法师域 | `master` / `master_credential` / `master_schedule` | 法师信息、资质、排班 |
| 服务域 | `service_type` / `temple_service` / `temple_service_slot` | 服务项目、结构化时段和容量模板 |
| 预约域 | `booking` / `booking_slot_inventory` / `booking_status_log` | 预约、日期时段库存、状态流转记录 |
| 商品域 | `product` / `product_sku` / `product_category` | 商品、SKU、分类 |
| DIY域 | `diy_design` / `diy_order` / `material` / `material_sku` | 设计、订单、材料库 |
| 订单域 | `shop_order` / `shop_order_item` / `logistics` | 商城订单、物流 |
| 财务域 | `finance_transaction` / `finance_ledger_entry` / `settlement` / `withdrawal` / `commission_config` | 平台总账、分账结算、提现、抽成 |
| 内容域 | `review` / `report` / `design_square` | 评价、举报、设计广场 |
| 系统域 | `role` / `permission` / `operation_log` / `dictionary` | 角色、权限、日志、字典 |

**数据隔离策略**:

| 数据类型 | 隔离策略 |
| -------- | -------- |
| 寺院数据 | 通过 `temple_id` 隔离，寺院管理员仅可查询本寺院数据 |
| 法师数据 | 通过 `master_id` 隔离，法师仅可查询本人数据 |
| 商城数据 | 商城运营仅可管理商品域和DIY域数据 |
| 平台数据 | 超管可访问全量数据，客服仅可访问投诉/举报相关数据 |

### 5.5 消息队列设计

**推荐方案**: RabbitMQ / RocketMQ

| 消息场景 | Topic/Queue | 生产者 | 消费者 | 说明 |
| -------- | ----------- | ------ | ------ | ---- |
| 预约通知 | `booking.notify` | 预约服务 | 消息服务 | 用户下单后通知寺院和法师 |
| 订单状态变更 | `order.status` | 订单服务 | 消息服务 + 财务服务 | 订单状态流转通知 |
| 加持派单 | `blessing.dispatch` | DIY/订单服务 | 寺院服务 | 加持服务派单到寺院 |
| 加持完成回传 | `blessing.complete` | 寺院服务 | DIY/订单服务 | 加持完成后回传状态 |
| 物流状态同步 | `logistics.sync` | 物流服务 | 订单服务 | 物流状态变更通知用户 |
| 评价通知 | `review.notify` | 评价服务 | 寺院服务 | 新评价通知寺院管理员 |
| 提现通知 | `withdrawal.notify` | 财务服务 | 消息服务 | 提现审核结果通知 |
| 内容审核通知 | `content.audit` | 内容审核服务 | 消息服务 | 审核结果通知用户/寺院 |
| AI问事请求 | `ai.divination` | AI服务 | AI服务 | AI对话消息处理 |
| 数据统计 | `analytics.sync` | 各业务服务 | 数据分析服务 | 异步统计数据汇总 |

**消息可靠性保障**:

1. 消息持久化：所有业务消息开启持久化存储
2. 消费确认：消费端手动ACK，处理失败进入死信队列
3. 消息重试：失败消息按指数退避重试，最多3次
4. 死信处理：超过重试次数的消息进入死信队列，人工介入
5. 幂等设计：消费端需保证幂等，避免重复消费

## 7. 开发优先级建议

### 7.1 分期规划

| 阶段 | 产品 | 核心模块 | 预计工期 | 说明 |
| ---- | ---- | -------- | -------- | ---- |
| **一期（MVP）** | 寺院管理台 | 仪表盘 + 寺院信息 + 法师管理 + 服务管理 + 预约管理 | 6-8周 | 打通预约闭环 |
| **一期（MVP）** | 法师工作台 | 工作台首页 + 日历 + 预约列表 + 消息中心 | 4-6周 | 法师可处理预约 |
| **二期** | 商城管理台 | 仪表盘 + 商品管理 + DIY订单 + 材料库 + 物流 | 8-10周 | 打通DIY+商城闭环 |
| **二期** | 平台总管理台 | 数据大盘 + 入驻审核 + 内容审核 + 财务管理 | 8-10周 | 平台运营能力 |
| **三期** | 全端 | 营销管理 + 数据报表 + 系统完善 + 性能优化 | 6-8周 | 运营体系完善 |

### 7.2 技术选型建议

| 层级 | 推荐方案 | 备选方案 |
| ---- | -------- | -------- |
| C端 App | 原生 Swift + SwiftUI | Flutter（跨平台） |
| Web管理台 | Vue 3 + Element Plus / Ant Design Vue | React + Ant Design |
| 法师小程序 | 微信小程序原生 / Taro | uni-app |
| API网关 | go-zero gateway | APISIX / Kong |
| 后端服务 | Java (Spring Boot) / Go | Node.js (NestJS) |
| 数据库 | MySQL 8.0 | PostgreSQL |
| 缓存 | Redis 7.0 | - |
| 消息队列 | RabbitMQ / RocketMQ | Kafka |
| 对象存储 | 阿里云OSS / 腾讯云COS | MinIO（自建） |
| 搜索引擎 | Elasticsearch | Meilisearch |
