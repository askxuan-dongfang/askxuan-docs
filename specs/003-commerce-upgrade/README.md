## 审计发现

- H5 加入购物车只有反馈，iOS/H5 均将库存作为销量展示。
- 总管理台缺少商城入口；积分列表缺少服务端搜索与状态过滤。
- DIY 缺少用户确认收货；商城退货缺少寄回和商家收货流程。
- 退款 outbox 使用临时 PAY-{orderId} 支付单号，必须改为服务端真实订单关联查询。
- 模拟支付与真实第三方支付需区分验收，避免将模拟成功当作真实扣款。

## 已交付行为

H5 购物车按账号持久化，商品、库存、价格在结算时重新校验；DIY 列表展示实际成交材料与价格，兼容历史设计快照。重试保留订单请求标识及已创建订单，继续支付不会重复创建。商品页和列表使用真实库存信息，移除没有服务依据的固定配送承诺，统一暖棕色页面、表单、状态卡和操作入口。

iOS 对齐购物车账号隔离、支付重试、售后申请/寄回、DIY 运单/收货、积分搜索。商城管理台补齐积分筛选、独立报表、退货收货、退款提交反馈和 DIY 退款状态。平台 `/admin/commerce` 集中查看现金商品/订单、DIY 材料/订单、积分订单、商城售后，提供详情和发货操作；现金订单销售、DIY 数量和积分消耗分别展示。

## 验证方式

- order、DIY、payment 三服务运行 `go test ./...`。
- 后端 `scripts/test-commerce-fulfillment.sh` 验证并发退货、权限与状态流转；`scripts/test-points-mall.sh` 验证积分、退款事务回滚与重复请求。
- 前端 `cd e2e && npx playwright test -c playwright.commerce.config.ts` 验证购物车、支付重试、积分与运营操作，覆盖移动端与桌面视口。
- 分别构建 H5、商城管理台、平台管理台及 iOS；iOS 的编译、真机安装与实际支付验收应分别记录。
- `scripts/audit-api-reference.mjs` 核对静态 routes.go 与 API Reference；动态注册接口还需通过业务请求验证。

## 验收边界

模拟支付、物流状态录入、页面可访问与第三方真实扣款、快递实际揽收是不同验收项。发布时应单独记录运行版本和回滚证据。平台经营统计沿用订单维度口径，不作为支付渠道对账账单。
